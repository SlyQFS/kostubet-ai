# KostubetAI — Руководство и архитектурный регламент для ИИ-агентов (AGENTS.md)

Документ описывает назначение, архитектуру, структуру кодовой базы, схему данных, правила модификации кода и рабочие процессы проекта **KostubetAI**.

---

## 1. Обзор проекта

**KostubetAI** — Telegram-бот с искусственным интеллектом на языке **Rust**, обладающий изолированной персональной памятью пользователей, модулем RAG (поиск по базе загруженных документов/гайдов) и многоуровневым контролем размера базы данных (жесткий лимит по умолчанию 1 ГБ).

### Ключевые возможности:
- **Совместимость с любыми OpenAI-совместимыми LLM API**: OpenAI, OpenRouter, Ollama, vLLM, LM Studio, DeepSeek и др.
- **Изолированная дословная память**: Каждый пользователь имеет персональный контекст (по умолчанию до 5000 токенов, ~15 КБ). История хранится дословно, без искажающих суммаризаций. Старые сообщения автоматически вытесняются.
- **База знаний (Гайды / RAG)**: Возможность загрузки текстовых файлов (.txt, .md, .csv, .json, .yaml и др. до 5 МБ) или добавления гайдов через Telegram-команды. Автоматический семантический поиск по ключевым словам и динамическое подмешивание релевантных выдержек в системный промпт.
- **Гарантированный лимит диска (1 ГБ)**: Отслеживание физического размера SQLite файла + WAL-журнала. При превышении 95% порога запускается 4-этапная каскадная очистка.
- **Интеллектуальная работа в группах**: В личке бот отвечает на всё; в группах — только при прямом теге `@bot_username` или ответе (reply) на сообщение бота.
- **Telegram UX**: Индикация набора текста (`Typing`), разбиение длинных ответов (>3900 символов) без разрыва слов и форматирование без Markdown-артефактов.

## 2. Стек технологий и зависимости

| Компонент | Технология / Крейт | Назначение |
|---|---|---|
| **Язык** | Rust (Edition 2021) | Высокая производительность, безопасность памяти, минимальный footprint |
| **Асинхронный Runtime** | `tokio` (1.x) | Мультипоточный runtime, таймеры, сигналы ОС (`SIGINT`, `SIGTERM`) |
| **Telegram Framework** | `teloxide` (0.14) | Long-polling диспетчеризация, роутинг команд и обновлений |
| **HTTP-клиент** | `reqwest` (0.12) + `rustls-tls` | Запросы к LLM API и скачивание документов через Telegram Bot API |
| **База данных** | `rusqlite` (0.32, `bundled`) | Встроенная SQLite с режимом `WAL` и поддержкой foreign keys |
| **Сериализация** | `serde` (1.x), `serde_json` (1.x) | Работа с JSON для LLM Chat Completions API |
| **Конфигурация** | `dotenvy` (0.15), `std::env` | Загрузка `.env` файлов и валидация переменных окружения |
| **Логирование** | `tracing`, `tracing-subscriber` | Структурированное логирование с фильтрацией через `RUST_LOG` |
| **Деплой** | Docker & Docker Compose | Multi-stage сборка на Alpine, не-root пользователь, persistent volumes |

- **[`src/memory.rs`](file:///home/slyqfs/ZCode/KostubetAI/src/memory.rs)**:

  - Метод `reply`: сохраняет запрос пользователя, извлекает историю в пределах лимита токенов, находит чанки гайдов, собирает системный промпт, вызывает LLM, сохраняет ответ, обрезает историю и проверяет дисковый лимит.

## 4. Архитектура данных (SQLite Schema)

База данных SQLite инициализируется автоматически со следующей схемой:

```sql
CREATE TABLE IF NOT EXISTS users (
    user_id       INTEGER PRIMARY KEY,
    first_seen    INTEGER NOT NULL,
    last_activity INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INTEGER NOT NULL REFERENCES users(user_id) ON DELETE CASCADE,
    role       TEXT    NOT NULL,
    content    TEXT    NOT NULL,
    created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_messages_user ON messages(user_id, id);

CREATE TABLE IF NOT EXISTS guides (
    guide_id   INTEGER PRIMARY KEY AUTOINCREMENT,
    title      TEXT    NOT NULL UNIQUE COLLATE NOCASE,
    added_by   INTEGER NOT NULL,
    created_at INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS guide_chunks (
    chunk_id    INTEGER PRIMARY KEY AUTOINCREMENT,
    guide_id    INTEGER NOT NULL REFERENCES guides(guide_id) ON DELETE CASCADE,
    chunk_index INTEGER NOT NULL,
    content     TEXT    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chunks_guide ON guide_chunks(guide_id);
```

## 5. Алгоритмы и бизнес-логика

### 5.1. Управление памятью пользователя
1. Оценка токенов производится по эвристике: `1 токен ≈ 3 символа` (с запасом для UTF-8 / русского языка).
2. При формировании контекста выбираются последние сообщения пользователя от свежих к старым, пока суммарная длина укладывается в бюджет `USER_MEMORY_TOKENS * 3` символов.
3. Сообщение пользователя сохраняется в БД *до* отправки запроса в LLM (чтобы запрос не терялся при сетевых сбоях).
4. После сохранения ответа ассистента функция `trim_user_history` выполняет удаление старых сообщений пользователя через оконную функцию SQLite (`SUM(length(content)) OVER (...)`), удаляя всё, что превысило бюджет.

### 5.2. Поиск и интеграция гайдов (RAG)
1. Текст гайда нарезается на чанки по ~1200 символов с привязкой к абзацам (`\n\n`).
2. При вопросе пользователя из его текста извлекается `HashSet<String>` значимых слов (длина >= 3 символов, lowercase, non-alphanumeric split).
3. Производится подсчет пересечений слов с каждым чанком гайдов.
4. Чанки с наибольшим скором (до суммарного лимита 4000 символов) добавляются в системный промпт с пометкой `— Из гайда «{title}»:\n{chunk}`.
5. Если релевантных чанков нет, промпт содержит только базовые правила, экономя токены.

### 5.3. 4-этапная очистка дискового лимита (`enforce_limit`)
При превышении 95% от `MEMORY_LIMIT_MB` последовательно выполняются этапы очистки до тех пор, пока размер файла + WAL не станет `<= 95%`:
- **Этап 1**: Урезание историй **всех** пользователей до ~1000 токенов (3000 символов) + `VACUUM` + `wal_checkpoint(TRUNCATE)`.
- **Этап 2**: Урезание историй всех пользователей до ~100 токенов (300 символов) + `VACUUM`.
- **Этап 3**: Удаление записей всех пользователей, кроме 500 наиболее недавно активных (`ORDER BY last_activity DESC LIMIT 500`) + `VACUUM`.
- **Этап 4**: Удаление самых старых гайдов по одному (до 50 за один вызов функции) + `VACUUM`.

## 6. Правила разработки и стандарты для агентов

При внесении изменений в репозиторий ИИ-агенты **обязаны** следовать этим правилам:

1. **Безопасность и обработка ошибок**:
   - Запрещено использовать `.unwrap()` и `.expect()` в ветках рантайм-логики (за исключением инициализации в тестах или старта приложения при фатальных невалидных конфигах).
   - Всегда обрабатывать возможный poison мьютекса: `self.store.lock().unwrap_or_else(|p| p.into_inner())`.
   - Ошибки Telegram API не должны приводить к падению бота — логировать через `tracing::error!` или `tracing::warn!`.

2. **Сохранение UX Telegram**:
   - Системный промпт предписывает модели генерировать простой текст без Markdown-разметки (звездочки, решетки, бэктики), так как бот отправляет сообщения в plain text режиме.
   - Длинные сообщения обязательно отправлять через `send_chunks` / `split_telegram` с паузой 250 мс, чтобы не получать `FloodWait` от Telegram.
   - На длительных операциях (LLM генерация, скачивание файлов) обязательно поддерживать активность `spawn_typing`.

3. **Работа с базой данных**:
   - Не изменять схему БД без обратной совместимости или создания понятной миграции.
   - Всегда помнить о наличии каскадного удаления (`ON DELETE CASCADE`) при удалении пользователей и гайдов.
   - Любые операции с диском и очисткой должны вызывать `wal_checkpoint(TRUNCATE)` и `VACUUM` для возврата страниц ОС.

4. **Тестирование**:
   - Все новые алгоритмы форматирования, парсинга, поиска и работы с БД должны сопровождаться unit-тестами в блоке `#[cfg(test)] mod tests`.
   - Перед завершением задачи агент обязан выполнить `cargo test` и убедиться, что все тесты проходят без ошибок.

## 7. Команды для сборки, тестирования и запуска

```bash
# Проверка типов и линтинг
cargo check
cargo clippy --all-targets

# Запуск всех unit-тестов
cargo test

cargo run

# Локальный запуск в оптимизированном release-режиме
cargo run --release

docker compose up -d --build

# Просмотр логов контейнера
docker compose logs -f

# Остановка контейнера
docker compose down
```
